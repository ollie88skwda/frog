SBL end-to-end tests

Two suites verify the core loop without manual device testing:

  1. Playwright web suite (e2e/web.spec.ts) — runs fully headless and repeatable today. Drives the real app screens compiled to web.
  2. Maestro device flow (e2e/flows/core-loop.yaml) — the most faithful; covers the whole loop including set logging and ghosts. Needs a JDK + a native dev build (see below).

Quick start (web — the overnight-runnable one)

npm run e2e        # builds the E2E web bundle, then runs Playwright
npm run e2e:headed # same, with a visible browser

First time only, install the Chromium browser Playwright drives:

npx playwright install chromium

What the core loop is

  1. Library → add an exercise → it appears in the list.
  2. Train → Start session → pick the exercise → log 2 sets.
  3. Start a second session → pick the same exercise → prior numbers show as greyed “ghost” placeholders.
  4. Relaunch → logged data persists (offline SQLite).

* Known web gap. The session screen logs a set from TextInput.onEndEditing. react-native-web does not implement onEndEditing (zero references in the package), so on web the handler never fires — no set is logged, and the ghost prefill (which reads logged sets) never appears. This is a real app/runtime gap, not a test artifact. The web suite asserts it explicitly in the KNOWN WEB GAP test so a future fix (handling blur on web) is caught and the test can be promoted to a full ghost assertion. Until then, set-logging + ghosts are verified on-device (Maestro) and at the unit level (Vitest).

How the web suite works (and why)

The app stores data in on-device SQLite via expo-sqlite through Drizzle. On web, expo-sqlite’s synchronous API (openDatabaseSync) relies on a busy-wait worker handshake that reliably times out on the first call (Sync operation timeout), which crashes the app at boot. The screens call getDb() synchronously, so an async driver can’t be swapped in without changing app source.

For E2E we therefore back Drizzle with sql.js (a synchronous WASM SQLite) instead. This is a driver swap only — the schema, the migration SQL, every src/db/* query function, the session reducer, and all three screens are the real app code, unchanged. Wiring:

  • e2e/web/test-client.ts — sql.js-backed getDb(); persists the DB to localStorage after every write so a reload == an app relaunch.
  • e2e/web/entry.ts — initialises sql.js (async) and runs the migration before rendering, then renders the real expo-router app.
  • index.js (the package.json main) — delegates to expo-router/entry normally; loads the E2E entry only when EXPO_PUBLIC_E2E=1 (the dead branch is stripped from production bundles).
  • metro.config.js — when EXPO_PUBLIC_E2E=1, aliases src/db/client → the test client. Inert otherwise.
  • app.config.js — wraps app.json verbatim; only forces web output: "single" (SPA, no Node prerender) for the E2E build.
  • e2e/web/serve.cjs — serves the exported dist-e2e plus the sql.js wasm; e2e/playwright.config.ts launches it.

None of this affects the shipped app: every alias/branch is gated on EXPO_PUBLIC_E2E.

The only app-source change

Per the test plan, the sole edits to app screens are minimal testID props on interactive elements (input, buttons, exercise rows, set inputs). They render as data-testid on web and as accessibility ids on native, so both suites use the same selectors. No business logic was changed.

Maestro device flow (full loop, incl. set logging + ghosts)

Most faithful, but it needs a JDK and a native dev build, so it does not run in a bare headless CI box without setup.

# 1) JDK (Maestro needs a JRE) + Maestro
brew install --cask temurin            # needs admin; or any JDK
curl -Ls https://get.maestro.mobile.dev | bash
export PATH="$PATH:$HOME/.maestro/bin"

# 2) Native dev build on a booted simulator (Expo Go is not reliable for Maestro)
sudo gem install cocoapods             # one-time
npx expo run:ios                       # builds + installs; bundle id com.anonymous.sbl

# 3) Run the flow
maestro test e2e/flows/core-loop.yaml
# override the app id if your build differs:
maestro test -e APP_ID=com.you.sbl e2e/flows/core-loop.yaml
