01Vision & Positioning

Existing gym apps are trackers: record sets, see last time. SBL is a lab notebook: every session is a controlled experiment where you log the work and the conditions around it (sleep, bodyweight, pre-workout carbs, caffeine, stress, meal timing), then learn which inputs correlate with better output. Two things make it genuinely different from everything on the market:

  1. Input→output correlation ("Findings") — quantified-self-style insight no mainstream lifting app offers. Lifters complain the science-based apps won't let them dig into their own data.
  2. Open, code-accessible data — export + a documented API + an MCP server + AI-buildable docs, so technical users plug their own data into their own dashboards and AI. This is a moat a "tracker that added a sleep field" can't easily copy.

Design soul: a scientific instrument that stays dead-simple. Power is one tap away, never in your face.

02Target User

Intermediate-to-advanced lifters who autoregulate (RIR), care about machine setups, and want to control variables — and, prominently, the quantified-self / technical slice of them who build dashboards and run their own AI analysis. We lean into power; a minimalist who only wants reps×weight still gets a clean, fast tracker.

03Top Priority: Lightweight & Fast

A first-class product requirement, not a nice-to-have (see CLAUDE.md). Speed comes from architecture, not language:

  • Local-first — all reads/writes hit on-device SQLite instantly; never block UI on network; sync in background.
  • Optimistic UI; visual feedback within ~100ms; animations on the UI thread (Reanimated), 60fps.
  • Minimal dependencies (audit before adding); watch bundle size + cold start; lazy-load non-critical screens; virtualize long lists; memoize hot paths.
  • Offline-first is mandatory (gyms have no signal).

04Goals & Non-Goals

Goals

  • Make logging a set faster than incumbents while supporting far more depth on demand.
  • Treat everything trackable (reps, weight, RIR, notes, custom metrics, conditions) as opt-in, typed data.
  • Ship the differentiator at launch (at least a primitive Findings surface).
  • Make data code-accessible and AI-buildable from early on.

Non-Goals (v1)

  • No social feed/following/public sharing.
  • No nutrition database / calorie counting (carbs etc. are simple manual numbers).
  • No wearable/HealthKit auto-import in v1 (manual entry; later candidate).
  • No AI/ML programming. Progression and findings are transparent, rules-/stats-based.
  • No Rust; one TypeScript stack across app, CLI, MCP.

06v1 Feature Detail

6.1 Fast logging

Start a session freestyle. Per set: reps × weight inline; RIR, notes, custom metrics behind a one-tap expand. Ghost prefill of last session's values (tap to accept). Rest timer auto-starts on logging a set. Tap-and-go is the 90% path. Delivers immediate value before Findings exists (retention bridge).

6.2 Session conditions (the lab-notebook inputs)

Session-level typed, custom condition variables (sleep h, bodyweight, pre-carbs g, caffeine mg, stress 1–10, last-meal timing, free-text meal note). Collapsed by default to a one-line chip (7.5h · 82kg · 90g · stress 3); expands to log/edit. Must be dead-simple (a few taps) or it won't be sustained. Scales get defined anchors (e.g. stress 1–10 with guidance) to reduce noisy self-report.

6.3 Custom metrics

Everything logged is a metric. Built-ins: reps, weight, RIR, notes. Custom typed metrics (number / scale / text / checkbox) enabled per exercise. Progressive disclosure keeps defaults minimal.

6.4 Findings teaser at launch

A visible, honest insight surface from day one — even heuristic ("your top sets average heavier on 7h+ sleep") — with a countdown ("3 sessions until your first finding"), a confidence indicator, and explicit "correlation, not causation." The full engine is v1.x; the presence of the payoff at launch is non-negotiable.

6.5 Custom exercises (minimal)

Create unlimited exercises so you have something to log against. A small pre-seeded list ships for convenience. Light optional tagging only in v1 — the full controlled-vocabulary joint-action system + program builder are deferred to v2.

07Developer & Integration Layer core pillar

A stated major focus. "Make the data so cleanly accessible and documented that someone can point their own AI at it and build a dashboard." Built API-first: the documented data layer is the canonical interface; the app is its first client.
  • Export — JSON / CSV / raw SQLite, offline, for analysis. Solid in v1.
  • Personal read API — Supabase auto-generated, row-level-secured REST, accessed via a personal access token.
  • MCP server (TypeScript) — thin wrapper so a user's AI client queries their sessions/conditions/sets and runs its own analysis. The centerpiece for "build using AI."
  • AI-buildable docs — documented stable schema + llms.txt + copy-paste examples, so a coding agent can build an integration from the docs.
  • Scope: v1 targets individual power users building against their own data (personal token + MCP). A public OAuth API for third-party apps serving other users is a larger v2 commitment.
  • API/CLI/MCP read from the cloud → require an account + sync. Export works offline from the device.

08Data Model (API-first, documented)

Designed now for external consumption: stable, durable IDs, typed metrics, documented fields. Every table carries id, updated_at, soft-delete deleted_at, and a sync dirty flag (last-write-wins).

09Architecture

  • App: Expo (React Native) → iOS + Android via EAS. UI: NativeWind + react-native-reusables + Reanimated.
  • Local store (source of truth): SQLite via Drizzle → fully offline.
  • Cloud: Supabase (Auth + Postgres + auto REST API + RLS). Account optional; sign in to enable sync + API access.
  • Sync: last-write-wins per record (updated_at + soft-delete + dirty flag), background.
  • One language: TypeScript across app, CLI, and MCP server. No Rust.
  • Keep correlation/sync logic in clean, isolated modules (portable, testable; extractable later if ever needed).
  • Units: kg/lb user setting; stored canonically, displayed per preference.

10Design System — "The Lab Notebook"

A dark "instrument" look evolved into a science/lab-notebook identity; references pulled from outside fitness (lab notebooks, blueprints, terminals, Bearable/Oura, Notion/Bear).

  • Graph paper is a surface, not décor: inputs/sections are discrete boxes whose interior is graph paper, the grid filling each box edge-to-edge — one clean grid per box, no second/overlapping grid bleeding through.
  • Mono numerals, units always shown (tabular figures, columns never shift); notes as // comments; small-caps figure labels; conditions as fill-in lines.
  • Progressive disclosure everywhere; reduce cognitive load; no glassmorphism/translucency behind data.

11Key Risks & Mitigations from council

  • Statistical validity (n-of-1, noisy, low-n → spurious correlations, confounds, multiple comparisons). Mitigate: minimum-n thresholds before showing a finding, visible confidence, conservative effect-size display, honest causation caveats. Phase 0 tests this before we build.
  • Garbage-in (self-reported sleep/stress is noisy). Mitigate: defined scale anchors, fast consistent entry, and the dev layer lets power users export raw data and run their own rigorous analysis.
  • Retention before Findings matures. Mitigate: fast logging + ghost prefill deliver value immediately; Findings teaser + countdown create anticipation.
  • Competitive copy ("Hevy adds a conditions field"). Mitigate: the moat is the open/code-accessible data + MCP + notebook identity + depth, not the conditions field alone.
