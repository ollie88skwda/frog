# DECISIONS.md — Frog decision log

Terse, dated log of product/design/architecture decisions. **Rule: when a new decision overrides an old one, edit the old entry in place — mark it `SUPERSEDED → [see entry]` — so this file never contradicts itself.** Add an entry in the same commit as the change it describes.

## Product

- **2026-06-20** — Frog is a training lab notebook: log work + conditions, surface correlations ("Findings") with transparent stats, no AI/ML black boxes. Second moat: open data (export, PAT API, MCP). PRD: `docs/superpowers/specs/2026-06-20-frog-prd.html`.

- **2026-07-28** — **The `sbl` identifier layer is renamed to `frog`** (supersedes the 2026-06-20 placeholder entry and the "technical identifiers deliberately unchanged" clause of 2026-07-16). The display layer was already Frog; this finishes the job: package scope `@sbl/*` → **`@frog/*`**, root package `sbl` → **`frog`**, MCP bin `sbl-mcp` → **`frog-mcp`**, env prefix `SBL_*` → **`FROG_*`**, PAT prefix `sbl_` → **`frog_`**, E2E bridge global `__sbl` → **`__frog`**, SW cache → `frog-shell-v1`, notification tags → `frog-push`/`frog-rest`, local Supabase `project_id` → `frog`. Export filenames now derive from `APP_NAME` instead of hardcoding a brand. **Rationale for doing it now rather than never:** the earlier "API break with no user-facing value" reasoning assumed a live surface to break; there is none — `api_tokens = 0` (no PAT has ever been minted), `push_subscriptions = 0`, one user, zero deployed Edge Functions, and **nothing named `sbl` exists inside Postgres** (no schema, role, policy, function, or stored value). The break is free today and gets monotonically more expensive. **Persisted keys took the cautious path where a real user's browser holds the data**: `frog.sdraft.*` reads the legacy `sbl.sdraft.*` key as a fallback (and clears both, or a restored draft would outlive the commit that cleared it) and `frog:promo:*` reads the legacy dismissal — both marked deletable one release out. **`sbl.pastUsers` is deliberately NOT renamed**: nothing writes it, it is a read-only tombstone for pre-Clerk data on real devices, and renaming it means that stale entry is never cleaned up. `sbl_`/`SBL_*`/`sbl-mcp` took a **hard cutover** (no dual-accept) because the compat shim would guard nothing: zero tokens exist and `packages/mcp` is `private` and unpublished, so the only reachable configs are hand-written local ones. **`bun.lock`'s root workspace `name` still reads `sbl`** — bun 1.3.14 won't refresh that one field on an incremental install, and forcing it means deleting the lockfile, which re-resolves and bumps ~20 unrelated deps (biome, playwright, supabase-js): a supply-chain change, not a rename. Harmless (`bun install --frozen-lockfile`, what CI runs, passes) — don't "fix" it by deleting the lockfile. **Not part of this change:** the GitHub repo name, the Supabase project display name, and above all the **Vercel project name — renaming it changes the deployed origin (`sbl-sepia.vercel.app`), which is the security boundary for every browser-persisted key above; an origin change orphans all of them at once regardless of what the code says.** Attach a real custom domain before ever renaming that project.

- **2026-07-27** — **Voice set logging fills, never commits.** A mic button in the session header (`voice-log-mic`) takes one spoken utterance ("rear delt flies 250 lbs for 5 reps") and fills the matching block's **active row** — commit stays an explicit user action (Enter / Add set), because a mishearing that auto-logged a set would be worse than one the user can see and correct before committing. Pipeline: `parseSetUtterance` (`packages/core/src/domain/voice-parse.ts` — plain regex, no NLP dep; the connector for/x/by and the unit word are both optional) → `matchExerciseName`/`isConfidentMatch` (`domain/match-exercise.ts`) against **this session's own blocks only**, never the full library → an imperative `ActiveRowHandle.applyVoice` on the target row. **Unit precedence**: spoken unit word > the block's per-exercise `exercise_prefs` override > the session unit (one shared `blockUnitFor`, so the grid and the voice round-trip can't disagree); storage stays kg. **Ambiguity asks instead of guessing**: no confident match, or two blocks tied (same exercise logged twice), opens `VoiceMatchPicker` scoped to those blocks, duplicate names discriminated by session order ("Bench Press (2nd)"). Mic failures are routed, not flattened: `not-allowed` reads as blocked-permission, `network`/`audio-capture`/`service-not-allowed` as a recognition outage (Chrome's implementation is server-backed) — only genuine misses say "didn't catch that". The button is feature-detected on `isSecureContext` + `SpeechRecognition`/`webkitSpeechRecognition` (Firefox has none, iOS Safari is inconsistent) rather than rendered dead. e2e: `e2e/voice-log.spec.ts` — the recognition constructor is stubbed at page init (real audio can't be driven from Playwright); everything downstream of the transcript is the real code path.
- **2026-07-30** — **Home's hero is "today's plan", not a Start button — and "programs" stay the routines we already have.** The Home quick-start row (a status line plus a small `Start` chip) is replaced by `apps/web/src/components/home-hero.tsx`, the screen's headline element: an accent-tinted eyebrow (`Today's plan`, or `Next in {program}` when an active program is driving the choice), the **routine name at 26px**, a data line (`5 exercises · 15 sets · last 4d ago`), a **preview of the first four exercises with their prescribed sets** — the whole point being that the work already exists — and a full-width 56px accent CTA reading `Start {routine}`. Underneath, a horizontally-scrolling strip of every other pre-saved routine (name + last-done) re-aims the hero in one tap, ending in a dashed `New routine` chip; `Empty session` stays as a quiet ghost button, because an unplanned session must never become hard. **No new tables or concepts:** a "named, reusable plan" is already `routines` (+ `routine_folders`), and `programs` is already a distinct first-class thing — a provenance row tying one folder of materialized routines to a catalog key or generator config (2026-07-15 M2/M11 entries). So this task is *surfacing*, not modelling: the hero reads `listRoutines` + `activeProgram` + session provenance (`sessions.routine_id`), and the only new server call is `getRoutineDetail` for the one routine being previewed. **What "today" is comes from one shared rule** — `suggestRoutineId` in `packages/core/src/domain/plan.ts`: the routine whose last *completed* session is oldest (never-completed sorts oldest, ties by display position), confined to the active program's folder while that folder has live routines. That rule was **not invented here** — it is the Trainer's existing next-workout rule, and `lib/trainer.ts` now calls the same function instead of keeping its own copy, because two screens disagreeing about what today is would be a real bug (cf. the two unreconciled exercise matchers in AGENTS.md). Rejected: **strict A/B/C rotation** (advance past whatever you last did) — it is the more "programmed" answer, but it buries a skipped day forever and would have contradicted the Trainer; longest-neglected self-heals and still walks an authored order naturally through a completed cycle. Rejected: **persisting the day's pick** — overriding the suggestion is component state that resets on reload, so nothing can drift out of sync with what you actually logged. Rejected: a **dropdown** — it hides the alternatives behind a tap and shows no last-done signal. `start-session-btn` on `/train` is untouched (the whole existing suite asserts on it, `e2e/helpers.ts`'s `signIn()` included); Home's `home-start-btn` survives as the hero CTA. Covered by `e2e/home-hero.spec.ts` (phone viewport) plus a hero assertion in `e2e/programs.spec.ts`.
- **2026-07-30 (custom exercise adder)** — Users can create and edit their own exercises with the same fields the seed library has. Built from a discovery report's 12-step plan, with the captain overriding several of the report's own recommendations on its open questions (report §8).
  **Extend `exercises`, no new table.** Custom and book rows already share one table discriminated by `owner_id is null` / `is_custom`; a second table would fork every one of the ~12 existing read sites. Every new column (`mechanic`, `movement_pattern`, `laterality`, `default_reps_min`, `default_reps_max`, `default_rest_sec`, `notes`, `aliases`, `media_path`, `media_type`, plus `muscle_targets[].role`) is nullable with no default — a book row that never fills them behaves exactly as before, zero backfill.
  **Muscle role, not just array order.** `muscleTargets` entries gain an optional `role: "primary" | "secondary"` (`roleAt()` / `primaryMuscles()` / `secondaryMuscles()`, `domain/anatomy.ts`), so an exercise can declare **two primaries** (e.g. Romanian deadlift: hamstrings + glutes) instead of relying on "index 0 wins" alone. Absent `role` still resolves under that same index-0 convention for every pre-existing row — no backfill needed. Because reclassifying an exercise's muscles changes which of your *past* sets count toward which muscle in stats/Findings, the editor shows a one-line disclosure at the point of edit: "Changing muscles updates your past statistics too." Library grouping and generator matching still key off the first target regardless of `role` — role changes muscle credit and display, not which shelf an exercise lives on.
  **Tier stays off the create form.** S/A/B/C is an evidence-informed judgment call the app makes for seed exercises (`ACTION_RATINGS`); asking a user to self-rate a brand-new custom exercise on the same scale at creation time is asking them to grade their own homework. Tier is instead an **Advanced, edit-only** control (`exercise-editor.tsx`, gated on `mode === "edit"`) that defaults unset — the same "untiered, not S" semantics every unrated seed exercise already has. Fixed in the same change: `tierNameClass(null)` previously returned the *same* class as tier S (`text-ink`) — 862 of 882 seed rows and every custom exercise are untiered, so the bug rendered "unrated" as "Best" for nearly the whole library (commit `5c68662`).
  **Real upload storage for exercise media, not a `video_url` field.** The discovery report's own default (§4.1) was to ship a plain URL column and defer uploads; the captain overrode that — a demo photo/video attaches the same way machine photos and session photos already do: a private `exercise-media` storage bucket, RLS scoped to the owning user (`(storage.foldername(name))[1] = (select auth.jwt()->>'sub')` — the current pattern, not the older `auth.uid()` form), client-side resize before upload (`lib/photo.ts`, mirrors `machines.tsx`/`measures.tsx`), and signed-URL delivery (`uploadExerciseMedia` / `exerciseMediaUrl`, `repo/supabase.ts`). `media_path` + `media_type` (`image | video`, null = no media) replace the URL-field idea outright — it was never shipped.
  **The two independently-built fuzzy matchers are now one.** `generator/match-exercise.ts` (routine-paste import) and `domain/match-exercise.ts` (voice logging) had drifted into the same exported names with different shapes — the report flagged this as a standing risk and recommended deferring the merge; the captain called for merging it *now* instead, before alias-matching landed on top of two copies and made a three-way reconciliation later. `domain/match-exercise.ts` is the one survivor (barrel-exported: `matchExerciseName`, `sameExerciseName`, `normalizeExerciseName`, `isConfidentMatch`, `MatchCandidate`, `ExerciseMatch`); `MatchCandidate.aliases` lets a custom exercise's alternate names resolve the same way as its primary name for both callers. See the 2026-07-17 (routine paste) and 2026-07-27 (voice logging) entries above, both edited in place with `SUPERSEDED → 2026-07-30` markers per this file's own rule, rather than restated here.
  **One `updateExercise(id, patch: ExercisePatch)` replaces four narrow setters** (`setExerciseMachine` / `setExerciseClassification` / `setExerciseTypeEquipment` / `setExerciseTags`) that had been accreting one per newly-editable field. `ExercisePatch` covers every editable column including rename, which had no path at all before this. Collapsed now, per the captain, rather than letting a fifth or sixth setter join the pile as more fields land.
  **Discoverability stays inside the existing 3-tab structure** (Home / Training / Profile) — no 4th tab, which would reverse the 2026-07-14 navigation call and resize the floating tab island on a 390px screen for one new entry point. Three paths in instead: the session exercise picker's empty state (`Create "{query}"`, name prefilled from the search) and the routine-paste unmatched list both open the shared `ExerciseEditor` directly rather than sending a mid-workout or mid-import user away to Library and back; Training's Programs/Trainer grid becomes a 3-up with **Exercises**; and Home's Library card is promoted above Findings, retitled **Exercises**, and gets its own **+ New** deep link (`/library?new=1`, read once on mount and stripped from the URL) so create is one tap from Home instead of two.
  **PAT API / export exercise payload widened to the full row.** `GET /v1/exercises` (and the `exercises` field of `GET /v1/export`) hand-listed 7 columns against a table that had grown to 17 (now 27) — any new column silently missed the personal-access-token API, the MCP server, and `llms.txt` alike, since all three ultimately read through this one Edge Function. Fixed by dropping the hand-list for a bare `.select()`, matching every other resource (`sessions` / `metrics` / `session_exercises` / `set_logs`) already returned that way in the same file — removes the drift-prone pattern instead of just re-widening the list once more. `docs/schema.md`'s `exercises` table (previously missing 4 columns, now missing 10 more) and `docs/api.md` are updated in the same commit.

## Design

- **2026-07-30 (session grid shows every routine-configured set immediately, not just the one being logged)** — Bug report: start a routine with 5 sets configured on one exercise (all "6–8" reps) and the session shows exactly one editable row — "only 1 set... shows up." Confirmed end-to-end (real browser, real dev server, real local Supabase): `startRoutineSession` (`packages/core/src/repo/supabase.ts`) only ever writes `session_exercises` rows on session creation, never `set_logs` — that part is by design, not the bug (see the 2026-07-15 M2 session-slice entry, and `e2e/routines.spec.ts`'s "start routine prefills the grid" test). The actual gap: `ExerciseBlock` (`apps/web/src/screens/session.tsx`) rendered exactly one `ActiveRow`, seeded per index from the routine template as `block.committed.length` advances, with **no rendering at all for the sets that hadn't become active yet** — so a freshly started session showed "0 sets" and one input box even though 5 were configured, and the other 4 only appeared one at a time as each prior set was logged. Nothing was lost (logging through sequentially does write all 5 correctly), but the routine's own plan was invisible until you'd already stepped through it. **Fix is additive, not architectural**: a new read-only `UpcomingRow` renders `seedSets.slice(activeIndex + 1)` — the remaining routine/copy-seed targets — as muted preview rows (`upcoming-{index}[-{col}]` test ids) below the active row, so all N configured sets are on screen the instant the session starts and the list shrinks by one each time a set commits. The single-active-row **commit mechanic is unchanged** (still the only way real `set_logs` rows get written — no schema change, no eager materialization). **Rejected**: eagerly writing all N `set_logs` rows at session-creation time with a planned-vs-performed flag — a `set_logs` semantics change touching ~10+ read call sites (records/PRs, delete-cascade, session-reducer) for what reads as a purely visual gap; that's a bigger, separately-sequenced call, and it overlaps the routine-builder RIR-range/add-set-with-inherited-range revamp being scoped in parallel — noted for whoever sequences that follow-up, not bundled into this fix. e2e: new "materializes every configured set as a visible row" case added to `e2e/routines.spec.ts`.
- **2026-07-30 (rest timer is its own control)** — **The rest timer is split into a header *control* and a docked *countdown*, and stops sharing space (or a menu) with the block's ⋯.** Measured before, at 390×844: the running countdown was a **152×32 px chip inside the exercise block header** — jammed between the truncated exercise name, the "N sets" count, the ⋯ and the ✕, five controls in a 356 px row — and its target presets were a **section inside the ⋯ menu**. So the timer had no affordance of its own anywhere: at rest it was invisible, and while running it read as more ⋯-menu furniture. (**Not reproduced:** the report of an overlay covering the bottom sixth of the screen. At 390×844 the chip sat at y=118, 3.8% of viewport height, nowhere near the bottom. The *entanglement* half of the report is exactly right and is what this fixes.) **Now: (1) `RestControl`** — a bordered button in the block header, immediately left of the ⋯, 40 px tall on mobile (`md:h-8` — the voice-mic precedent at the time; the mic itself went to a uniform 40 px `icon-lg` on 2026-07-30 (session-page cleanup), this control did not). Dispatch is a bounded worker pool (4 in flight) over `mutateAsync`, not an unbounded `for` loop: a 200-line dictation dump otherwise opens 200 concurrent PostgREST inserts (×4 with the global mutation `retry`). **The pool bounds the network only** — submitting first seeds every pasted name's optimistic row in one cache write (`useSeedExercises()` in `queries.ts`, which pre-generates the ids the creates then run under), so a 200-name paste is on screen whole rather than trickling in four at a time behind the worker slots; `useCreateExercise`'s own `onMutate` is idempotent by id so it doesn't re-add a row it was seeded. The trigger (and submit) stay **disabled until the library list is present** (`data !== undefined`): duplicate detection reads that list, so during the cold ~1 MB load "Skip duplicates" would silently protect nothing and re-create every name the user already has (there is no name uniqueness constraint in Postgres); if that query ultimately fails with nothing fetched, the trigger stays blocked but says so and offers a refetch rather than claiming to still be loading. The gate is on **data presence, not query status** — TanStack Query v5 keeps `data` when a *background refetch* fails and only flips `status` to error, and every bulk run ends in an `invalidateQueries(["exercises"])` whose refetch can fail, so gating on `isSuccess`/`isError` would disable the trigger (and the open dialog's submit, mid-typing) with the whole library sitting on screen. Presence is only trustworthy because **optimistic writes update the exercises cache but never create it** (`updateExerciseRows` in `queries.ts` returns `undefined` — a documented `setQueryData` no-op — when the entry is absent): the single-add form stays live during the cold load, and a `(old = [])` updater would otherwise *build* the list out of that one optimistic row and unlock bulk add against it — the exact duplicate-everything failure the gate exists to prevent. The status flags can't stand in for this: `setQueryData` dispatches a `success` action, so it bumps `dataUpdatedAt`/`dataUpdateCount` and would satisfy `isFetched`/`isFetchedAfterMount`/`dataUpdatedAt > 0` just the same. For the same reason `useCreateExercise` only calls `cancelQueries` in `onMutate` when there *is* data — cancelling the cold fetch reverts it without restarting, so the library would sit empty until that create's own invalidate re-downloaded it. The optimistic row is not lost meanwhile: it is in the pending registry, so it merges in if the list lands before the create settles. `onSettled` then cancels **before** it invalidates, because `invalidateQueries` only cancels an in-flight fetch when the query already has data (`Query#fetch` gates `cancelRefetch` on `state.data !== undefined`): during the cold load the invalidate would otherwise be handed the running fetch's promise, and that pre-insert payload clears `isInvalidated` — so the exercise the user just added would be missing from the list for `staleTime` and they'd add it again. With data present the cancel is what the invalidate would have done anyway (optimistic writes update the revert state, so nothing optimistic is dropped), leaving the bulk-add path unchanged. Seeding up front means an exercise can be in the list for the whole run before its INSERT is dispatched, and `session_exercises.exercise_id` is a **real FK** — so optimistic exercise rows are registered in `apps/web/src/lib/pending-exercises.ts` (a `useSyncExternalStore` module, not the query cache: it tracks a write in flight, not server data) from seed/`onMutate` until `onSettled`, and every surface that would write a reference to an exercise id renders those rows inert until it clears: the session exercise picker ("Saving…"), the routine builder's picker, and on the library row itself the favorite star plus the expand toggle (the panel behind it edits tags, set metrics, machine and archive state — all keyed by an id Postgres doesn't have yet; `exercise_favorites`, `metric_exercises` and `routine_exercises` are all real FKs, and a rejected write there flips the control back with no message). The list still shows the rows immediately — only writes against them wait. That registry holds the **row**, not just the id, and `useExercises` re-applies any still-pending row missing from the list via `select`: seeded rows sit in the cache unprotected until their own create dispatches, so a refetch landing mid-run (window refocus at `staleTime` 15 s, or any sibling exercise mutation's invalidate) would otherwise replace the cache with server truth that predates them and the paste would trickle back in four at a time — exactly what seeding exists to prevent. `onError` drops the row from the registry before rolling it out of the cache, so a failed create can't be resurrected by that re-apply. Names whose create ultimately fails are surfaced under the trigger after the run — the dialog closes optimistically, so a partial failure would otherwise be invisible — and reopening the dialog prefills the draft with the **full** failed list (not the truncated preview), which is what makes "try again" a working path rather than a dead end; overlapping runs append rather than overwrite, so an earlier run's failures survive a later submit. That notice lives in its own module store (`apps/web/src/lib/bulk-add-failures.ts`, same `useSyncExternalStore` pattern) rather than dialog state: the run outlives the dialog *and* the screen (`mutateAsync` keeps dispatching, with `retry: 3` behind it), so component state would silently drop the notice for anyone who navigates away from the library mid-run. It is **dismissable** (×) — surviving unmount otherwise means surviving the whole session, and "not retrying these" is a normal outcome; dismissing is the only thing that clears it short of the next run, so the retry prefill can't be lost by merely opening and closing the dialog. Both stores hold **per-user** state outside the query cache, so they register a reset in `apps/web/src/lib/user-scoped-state.ts` that `auth.tsx` fires next to `queryClient.clear()` on sign-out and on any user change — `clear()` doesn't reach module state, and these rows are merged back *over* server data now, so user A's pending rows and failed names would otherwise surface in user B's library on the same tab (sign-out is SPA-only; no reload). Registration is by import rather than `auth.tsx` reaching into each store: a store nobody loaded holds nothing to reset, and it keeps the lazy-route-only failure store out of the eager bundle. A user change also retires any in-flight run (epoch bump) so its remaining inserts don't land in the new account. Rows are `memo`'d with stable callback props: each create still settles on its own, so a run re-renders the screen once per name, and ~900 unmemoized rows would reconcile on each. Because bulk add fires concurrent creates, `useCreateExercise` (a) rolls back on error by removing only its own optimistic row by id — a whole-cache snapshot restore (the pattern the other `queries.ts` hooks keep) would clobber sibling optimistic rows — and (b) keeps its own in-flight-create count (module-level `WeakMap` keyed by the `QueryClient` in `queries.ts`, bumped in `onMutate`, dropped in `onSettled`) so `onSettled` only invalidates `["exercises"]` when it is the last create out: an earlier settle would refetch server truth that predates its siblings' inserts and overwrite their optimistic rows, and would re-download the ~1 MB library once per name. The count is kept by hand rather than read back off the mutation cache (`isMutating`) because a mutation still reads `pending` while its own `onSettled` runs — two creates settling in the same microtask drain would each mistake the other for a live sibling and neither would invalidate. The invalidation is fired, not awaited, so a create dispatched during that ~1 MB refetch can still see the count reach zero. Tooling only — no real exercise names are authored here.

- **2026-07-30 (session-page cleanup)** — **`logSet` is idempotent on the caller's optimistic id; e2e defaults to a touch device.** **The reported duplicate set was not the auto-checkoff.** "Weight + reps + checkmark creates a duplicate row" was suspected to be a regression from the auto-checkoff-on-blur entry above; driven through a real browser at phone viewport (mouse, keyboard-tab and touch-tap) it does **not** duplicate — `commit()`'s `done.current` ref already guards double-commit, and the blur path is separate code.
