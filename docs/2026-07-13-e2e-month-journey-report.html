SBL — Month-in-the-Life E2E Campaign

Drove ~a month of real training through the app so the coaching features had enough history to activate — then verified every screen and flow end-to-end.

July 13, 2026 · exploratory run, real browser + real local Supabase · all core flows verified

Bottom line: the app works. A simulated month of 20 sessions — logged through the real UI — lit up all four progression trends, both sleep→performance correlations, and the countdowns, exactly as the math predicts. Along the way I found and fixed one real product bug (deleted workouts leaking into prefill) and two flaky test races. Zero console errors across every screen, light and dark, desktop and mobile.

How it was tested

A real user doesn't get coaching on day one — the findings engine needs history (≥5 sessions per exercise for a trend, ≥10 condition-tagged sessions for a correlation). So I simulated a month:

  • 4 weeks, 20 sessions, an upper/lower split with sleep logged each day. Weights were chosen so the engine must produce specific verdicts.
  • 6 sessions driven fully through the UI (start → pick exercises → type every set → log conditions → end), covering every distinct interaction once. The other 14 were bulk-inserted or imported to hit a month of history fast.
  • Dates were backdated (the UI can't backdate; that itself is a finding) via the Hevy CSV importer and the test data hook, spreading sessions across 32 days.
  • Every number was pre-checked against the real @sbl/core findings engine before driving, so the end state was deterministic.

The bug: deleted workouts leaked into prefill

What I found. When you delete a session, the app soft-deletes the session row but not its exercises or sets. Those orphaned rows stay "live" — and the ghost-prefill feature (which pre-fills your next set from your last workout) reads them. Result: a workout you deleted can still prefill your next session, or blank it out.

Root cause · packages/core/src/repo/supabase.ts — deleteSession() was a one-line soft-delete of the sessions row. lastSetsForExercise() (ghost source) queries session_exercises without checking the parent session, so orphaned children surfaced. It also leaked deleted workouts into JSON/CSV export.

The fix cascades the soft-delete to the session's session_exercises and set_logs. Verified end-to-end: log a distinctive Squat session → delete it → confirm its exercises and sets are now soft-deleted and the next session's ghost falls back to the correct prior workout (117.5 kg), not the deleted one.

Also fixed — two flaky test races

Two existing E2E specs read the database immediately after a fire-and-forget optimistic write, so under load they raced the write and failed intermittently (different tests each run). Fixed both to poll for the write, matching the pattern the codebase already uses elsewhere.

  • e2e/conditions-metrics.spec.ts — one-shot .single() lookup right after creating a custom condition.
  • e2e/machines.spec.ts — full-page navigation before the machine-link write landed.

Flagged (not changed)

  • minor Rapid tag entry can drop a tag. Adding two tags in quick succession: addTag() appends to the cached tags before the re-render lands, so the second add can clobber the first. A real user's typing delay avoids it; worth a state guard if tags get heavier use.
  • cosmetic Findings prose reads "on high Sleep (h) days" — the unit suffix in the metric name is slightly awkward inline. Purely wording.
  • note Sessions can't be backdated in the UI at all (start hardcodes "now"). Fine for logging, but worth knowing — importing is the only way to add past workouts.

Notes on the run

The dev machine was heavily loaded (load ~13 on 10 cores) during the run, so drivers used generous 20-second waits and the same optimistic-write polling the app relies on. Local Supabase was reset a couple of times mid-run (new migrations were added), which wiped journey data — each time I re-seeded and re-ran on a fresh user. The results above are from clean, stable runs. Leftover test users/sessions remain in the local DB; a supabase db reset clears them.
